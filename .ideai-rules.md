## Brand and Naming Standards

### Brand Name: IdeaI

**CRITICAL**: The product/brand name must ALWAYS be written as **IdeaI** (exact capitalization: capital I, lowercase dea, capital I):

- ✅ Correct: `IdeaI`, `IdeaI web app`, `Welcome to IdeaI`, `IdeaI.Space`
- ❌ Incorrect: `IDEAI`, `Ideai`, `ideai`, `IDEAi`, `Idea I`, or any other variation

**Why this capitalization matters:**

- "Idea" (the word)
- "Ide" (part of idea)
- "An AI Ide" (an AI idea)
- "an ai idea engine"
- Also visually resembles "ideal" which is excellent for branding
- The URL `IdeaI.Space` works perfectly and looks sublime as text

**When to use IdeaI:**

- Product/brand name in UI text
- Documentation references to the product
- Code comments mentioning the brand
- User-facing content
- URLs and domain references

**Note**: Repository names, GitHub orgs, and technical identifiers may use lowercase (e.g., `ideai-main`, `ideai-dev-000`) for technical reasons, but the **brand name itself is always IdeaI** (exact capitalization).

### Semantic File Naming

**CRITICAL**: Semantic, descriptive file names are essential:

- ✅ Good: `user-profile-card.tsx`, `api-auth-handler.ts`, `deployment-checklist.md`
- ❌ Bad: `component1.tsx`, `utils.ts`, `file.md`, `temp.js`

**File naming principles:**

- Use kebab-case for file names
- Be descriptive and specific
- Include the purpose/type in the name
- Avoid abbreviations unless widely understood
- Group related files with consistent prefixes

### Documentation File Organization

**CRITICAL**: All documentation files must be organized in semantic locations. NO random MD files in root or scattered locations.

**Rules**:

- ✅ **All documentation in `docs/` directory** - Organized by category (deployment/, development/, architecture/, etc.)
- ✅ **Root README.md only** - Project overview, links to docs/
- ✅ **Temporary files archived** - Move to `docs/archive/temporary/` or `docs/archive/status/`
- ✅ **Semantic naming** - Use kebab-case: `pre-deployment-checklist.md`, not `PRE-DEPLOYMENT-CHECKLIST.md`
- ❌ **NO MD files in root** (except README.md, SECURITY.md, .ideai-rules.md, .cursorrules)
- ❌ **NO temporary status files in root** - Archive immediately after use
- ❌ **NO scattered documentation** - All docs must be in `docs/` with proper structure

**Documentation Structure**:

```
docs/
├── architecture/     # Architecture documentation
├── deployment/       # Deployment guides and checklists
├── development/      # Development guides
├── setup/           # Setup instructions
├── testing/         # Testing documentation
├── tools/           # Tool documentation
└── archive/          # Archived/temporary files
    ├── status/      # Status snapshots
    └── temporary/   # Temporary files
```

**Before Creating New MD Files**:

- [ ] Is it documentation? → Place in `docs/{category}/`
- [ ] Is it temporary? → Place in `docs/archive/temporary/`
- [ ] Is it a status snapshot? → Place in `docs/archive/status/`
- [ ] Does it follow semantic naming? → Use kebab-case
- [ ] Can it be used in docs site? → Store as `.md`, sync to `apps/docs/content/` if needed

**Cleanup Workflow**:

1. At end of each session: Review root for stray MD files
2. Move to appropriate `docs/` location
3. Archive temporary files immediately
4. Update documentation index if needed

### UniFrame (UF) Naming Standard

**CRITICAL**: UniFrame is the brand name. File names use `uf-` prefix. Code can use `uf` or `uniframe`.

**Brand Name**: UniFrame (capital U, capital F)

- ✅ Correct: "UniFrame by IdeaI", "UniFrame Component", "UniFrame Card"
- ❌ Incorrect: "Uni Frame", "uniframe", "UF" (when referring to brand)

**File Naming Rules:**

- File names: `uf.tsx`, `uf-code-viewer.tsx`, `uf-card.tsx` (kebab-case with "uf-" prefix)
- Directory names: `uf-card/`, `uf-components/` (kebab-case with "uf-" prefix)
- ✅ Correct: `uf.tsx`, `uf-code-viewer.tsx`
- ❌ Incorrect: `uniframe.tsx`, `UniFrame.tsx`

**Code/Import Naming Rules:**

- Component names: `UF`, `UFCodeViewer`, `UFCard` (PascalCase with "UF" prefix)
- Interface names: `UFProps`, `UFCodeViewerProps` (PascalCase with "UF" prefix)
- Import paths: Can use `uf` or `uniframe` - both work: `@repo/ui/components/uf` or `@repo/ui/components/uniframe`
- CSS classes: `uf-container`, `uf-card`, `uf-button` (kebab-case with "uf-" prefix)

**Documentation/Headers:**

- Headers and user-facing text: Use "UniFrame" (brand name)
- Code comments: Can use "UniFrame" or "UF" - both acceptable
- File headers: Use "UniFrame" in @fileoverview

**Why this matters:**

- Brand consistency: "UniFrame" in user-facing content
- Code efficiency: `uf` is shorter in code
- Flexibility: Both `uf` and `uniframe` work in imports
- Professional code quality requires strict naming discipline

**NEVER be sloppy with naming - it's a sign of unprofessional code.**

## Code Standards

### Code Headers

All code files must include rich, descriptive headers with:

- @fileoverview: Brief description
- @module: Module name
- @description: Detailed explanation
- @example: Usage examples
- @see: Related files
- @todo: Known issues or improvements

### Code Quality

- TypeScript strict mode
- All functions typed
- No `any` types
- Error handling for async operations
- Comments for complex logic

### No Legacy Support Policy

**CRITICAL**: IdeaI is building a future framework, not maintaining legacy code.

**Rules**:

- ❌ **NO legacy file format support** (e.g., `.ideai` files - only `.ideai.json`)
- ❌ **NO backward compatibility code** for deprecated formats
- ❌ **NO fallback to old formats** - if format changes, migrate immediately
- ❌ **NO "legacy mode" flags** or feature toggles for old behavior
- ✅ **ONLY current formats** - use `.ideai.json`, not `.ideai`
- ✅ **Clean migration scripts** - migrate once, then remove old format
- ✅ **Future-focused** - build for 2026+ best practices, not 2020 compatibility

**Why**: Legacy support is bloat. We're building a modern framework, not maintaining old systems. If a format changes, migrate and remove the old format immediately.

**Example**:

- ❌ Bad: `if (legacyFile) { readLegacy(); } else { readNew(); }`
- ✅ Good: `readNew();` (only new format supported)

## Commit Standards

### Commit Messages

**CRITICAL**: All commits must follow this exact format with ticket reference:

```
type(scope): detailed subject line

Detailed explanation of what changed and why.

- Specific change 1
- Specific change 2
- Specific change 3

Related: TICKET-XXX
```

**Commit Types**:

- `fix`: Bug fixes
- `feat`: New features
- `docs`: Documentation changes
- `refactor`: Code refactoring
- `test`: Test additions/changes
- `chore`: Maintenance tasks
- `deploy`: Deployment changes
- `style`: Code style changes (formatting, etc.)

**Scope Examples**:

- `web`: Main web app
- `docs`: Documentation site
- `ui`: Shared UI package
- `deploy`: Deployment scripts
- `config`: Configuration files
- `vercel`: Vercel configuration

**Ticket Reference**: Every commit must include `Related: TICKET-XXX` at the end, where XXX is the ticket number (e.g., TICKET-0.1, TICKET-1.2).

**Example Good Commit**:

```
fix(web): resolve sub-folder route 404 issue

Fixed Next.js App Router catch-all route that was returning 404
in production. Converted client component to use React's use() hook
for async params handling.

- Updated page.tsx to use use() hook instead of useEffect
- Fixed async params resolution
- Added error handling for route matching
- Updated TypeScript types for params

Related: TICKET-0.1
```

**Example Bad Commit (DON'T DO THIS)**:

```
fix: stuff
```

### Commit Signing in Non-Interactive Environment

**CRITICAL**: When committing in Cursor/AI tools (non-interactive):

1. Disable auto-sign: `git config --global --unset commit.gpgsign`
2. Make commit
3. Re-enable: `git config --global commit.gpgsign true`

This is required because GPG signing needs passphrase entry, which isn't possible in non-interactive environments.

## UI Consistency Standards

### CRITICAL: Centralized CSS Architecture

**ALL IdeaI apps MUST use centralized CSS from @repo/ui. NO custom CSS in apps.**

#### Centralized CSS Architecture

1. **Two-Layer System**:
   - **Base Layer**: `@repo/ui/src/styles/globals.css` - Tailwind base + standard utilities
   - **IdeaI Layer**: `@repo/ui/src/styles/ideai.css` - Custom IdeaI finesse and polish
   - **Both imported in every app's globals.css**

2. **Import Pattern** (MANDATORY for all apps):

   ```css
   /* In apps/*/app/globals.css */
   @import "../../../packages/ui/src/styles/globals.css";
   @import "../../../packages/ui/src/styles/ideai.css";
   ```

3. **NO Custom CSS in Apps**:
   - ❌ NO custom button styles in app CSS modules
   - ❌ NO custom hover states in app CSS modules
   - ❌ NO custom typography in app CSS modules
   - ❌ NO custom colors in app CSS modules
   - ✅ ONLY use standard Tailwind classes + CSS variables from `ideai.css`
   - ✅ CSS modules should be minimal - only app-specific layout adjustments

4. **CSS Modules Usage**:
   - CSS modules ONLY for app-specific layout adjustments
   - Use standard Tailwind classes directly (not custom ideai-\* classes)
   - Use CSS variables from `ideai.css` for shared values
   - Example: `.button { @apply border-slate-300 dark:border-slate-700; }`

5. **Adding New IdeaI Styles**:
   - Add CSS variables to `packages/ui/src/styles/ideai.css` (NOT app CSS)
   - Use `@layer utilities` for reusable utility classes
   - All apps automatically get the new styles via imports
   - Document new utilities in `docs/architecture/ui-consistency.md`

6. **Before Committing UI Changes**:
   - [ ] All shared styles added to centralized `ideai.css` (not app CSS)
   - [ ] All apps use identical Tailwind classes
   - [ ] CSS modules are minimal (only app-specific adjustments)
   - [ ] No duplicate CSS between apps
   - [ ] Test in all apps side-by-side to verify perfect consistency
   - [ ] Update documentation if adding new IdeaI utilities

7. **Documentation**:
   - See `docs/architecture/ui-consistency.md` for full standards
   - All IdeaI classes documented in `ideai.css` file header

## Debugging Standards

### CRITICAL: Always Check the DOM, Not Just Code

**Many issues are only visible in the rendered DOM, not in source code.**

#### DOM Inspection Workflow (MANDATORY for UI debugging)

1. **Before Making Changes**:
   - Navigate to both pages in browser (use `mcp_cursor-ide-browser_browser_navigate`)
   - Take full-page screenshots of both pages (use `browser_take_screenshot` with `fullPage: true`)
   - Capture DOM snapshots (use `browser_snapshot`)
   - Compare visually side-by-side

2. **During Debugging**:
   - Extract and compare HTML from both pages
   - Check rendered CSS by inspecting specific elements
   - Compare CSS files loaded

3. **After Making Changes**:
   - **ALWAYS** take new screenshots to verify visual consistency
   - **ALWAYS** check the DOM again to ensure classes match
   - **ALWAYS** verify rendered CSS is identical
   - Compare before/after screenshots

4. **Visual Testing Checklist**:
   - [ ] Both pages render identically
   - [ ] All classes match (except CSS module hashes)
   - [ ] All CSS files loaded are from same source
   - [ ] Footer renders identically
   - [ ] Header renders identically
   - [ ] Content renders identically
   - [ ] Button hover states match
   - [ ] Text colors match
   - [ ] Spacing/padding matches
   - [ ] Font sizes match

5. **Common Issues Found Only in DOM**:
   - CSS module hash differences (expected, but verify styles are same)
   - Browser-specific CSS differences
   - Dark mode auto-detection differences
   - CSS specificity conflicts
   - Missing or duplicate CSS imports
   - Incorrect CSS class names in rendered HTML
   - Browser default styles interfering

6. **Tools to Use**:
   - `mcp_cursor-ide-browser_browser_navigate` - Navigate to pages
   - `mcp_cursor-ide-browser_browser_snapshot` - Get DOM structure
   - `mcp_cursor-ide-browser_browser_take_screenshot` - Visual comparison
   - `curl` commands - Extract HTML/CSS for comparison
   - Browser DevTools - Inspect computed styles

**NEVER assume code is correct without checking the rendered DOM.**

## Architecture Standards

### CRITICAL: Composability and Parent-Child Semantics

**Why This Matters**: IdeaI is built on composable patterns that enable infinite extensibility. Every component, app, and system follows strict parent-child semantics for consistency, predictability, and maintainability.

#### Core Principles

1. **Composability First**: All components must be composable
   - ✅ Components can be nested and combined
   - ✅ Components have clear parent-child relationships
   - ✅ Components expose consistent APIs for composition
   - ❌ Monolithic components that can't be broken down
   - ❌ Components that don't follow parent-child patterns

2. **Parent-Child Semantics**: Every system has clear hierarchy
   - **Parent**: Container, orchestrator, or wrapper
   - **Child**: Content, element, or nested component
   - **Relationship**: Explicit and documented

3. **Pattern Consistency**: Use established patterns, never invent new ones
   - ✅ Follow existing patterns in `@repo/ui`
   - ✅ Use UniFrame structure (wrapper, header, body, footer)
   - ✅ Use IdeaI app structure (parent app, child apps)
   - ❌ Creating new patterns without justification
   - ❌ Mixing patterns inconsistently

#### Component Composability Patterns

**UniFrame Card Structure** (Standard Pattern):

```
Card (Parent)
├── Header (Child)
│   ├── Title (Child)
│   └── Badge (Child)
├── Body (Child)
│   ├── Content (Child)
│   └── UI Elements (Children)
└── Footer (Child)
    └── Actions (Children)
```

**Rules**:

- ✅ Always use wrapper → header/body/footer → content pattern
- ✅ Each level is a composable child of its parent
- ✅ Children can be nested infinitely
- ✅ Each component has a single, clear responsibility
- ❌ Skipping levels (e.g., content directly in card without body)
- ❌ Mixing responsibilities (e.g., header doing body's job)

**Example - Correct Pattern**:

```tsx
<UFCard>
  <UFHeader>
    <UFTitle>Title</UFTitle>
    <UFBadge>New</UFBadge>
  </UFHeader>
  <UFBody>
    <UFContent>Content here</UFContent>
  </UFBody>
  <UFFooter>
    <UFButton>Action</UFButton>
  </UFFooter>
</UFCard>
```

**Example - Incorrect Pattern** (DON'T DO THIS):

```tsx
<UFCard>
  <div>Title</div> {/* ❌ Skipped header level */}
  <div>Content</div> {/* ❌ Skipped body level */}
</UFCard>
```

#### App Architecture: Parent-Child Semantics

**Parent App** (`web`):

- **Role**: Container, orchestrator, main application
- **Responsibilities**:
  - Serves at root URL (`/`)
  - Embeds child apps via iframes
  - Manages navigation and routing
  - Provides shared infrastructure
- **Configuration**: `.ideai.json` with `role: "parent"` and `childApps: [...]`

**Child Apps** (all other apps):

- **Role**: Content, feature, or specialized application
- **Responsibilities**:
  - Serve specific functionality
  - Can run standalone or embedded
  - Detect iframe context automatically
  - Hide header/footer when embedded
- **Configuration**: `.ideai.json` with `role: "child"` and `parentApp: "web"`

**Rules**:

- ✅ Parent app embeds child apps, never the reverse
- ✅ Child apps are independent but can be embedded
- ✅ Child apps detect iframe context automatically
- ✅ Parent-child relationship is explicit in `.ideai.json`
- ❌ Child apps embedding other child apps (use parent instead)
- ❌ Circular dependencies between apps
- ❌ Child apps modifying parent app behavior

**Example - Correct Pattern**:

```json
// apps/web/.ideai.json (Parent)
{
  "role": "parent",
  "name": "IdeaI",
  "childApps": ["docs", "all", "nocss"]
}

// apps/docs/.ideai.json (Child)
{
  "role": "child",
  "name": "Documentation",
  "parentApp": "web",
  "localPort": 3001
}
```

#### File and Directory Naming: Parent-Child Semantics

**Scripts Pattern**: `ideai-[parent]-[child].mjs`

- **Parent**: Main category (e.g., `build`, `develop`, `deploy`)
- **Child**: Specific function (e.g., `verify`, `track`, `sync`)
- **Example**: `ideai-build-verify.mjs`, `ideai-develop-sync-docs.sh`

**Component Pattern**: `[parent]-[child].tsx`

- **Parent**: Main component (e.g., `uf-card`, `ideai-page-template`)
- **Child**: Sub-component (e.g., `uf-header`, `uf-body`, `uf-footer`)
- **Example**: `uf-card-header.tsx`, `ideai-page-template-footer.tsx`

**Directory Pattern**: `[parent]/[child]/`

- **Parent**: Main category (e.g., `uf-card/`, `ideai-build/`)
- **Child**: Specific component or module (e.g., `uf-header/`, `modules/`)
- **Example**: `uf-card/uf-header/`, `ideai-build/modules/`

**Rules**:

- ✅ Always use `[parent]-[child]` naming pattern
- ✅ Parent name comes first, child name second
- ✅ Use kebab-case for all names
- ✅ Be descriptive and semantic
- ❌ Inverted order (child-parent)
- ❌ Missing parent or child in name
- ❌ Non-semantic names (e.g., `component1`, `utils`)

#### Why These Patterns Matter

1. **Predictability**: Developers know where to find things
   - Scripts: `ideai-[category]-[function].mjs`
   - Components: `[parent]-[child].tsx`
   - Apps: Parent-child relationship in `.ideai.json`

2. **Composability**: Components can be combined infinitely
   - Card → Header/Body/Footer → Content → Elements
   - Each level is a composable unit
   - New features extend existing patterns

3. **Maintainability**: Clear hierarchy makes code easier to understand
   - Parent-child relationships are explicit
   - Patterns are consistent across codebase
   - Changes are localized to specific levels

4. **Scalability**: Patterns scale to any size
   - Add new child components to existing parents
   - Add new child apps to existing parent app
   - Extend patterns without breaking existing code

5. **Onboarding**: New developers understand structure immediately
   - Patterns are self-documenting
   - Naming conventions reveal relationships
   - Examples show correct usage

#### Pattern Enforcement

**Before Creating New Components**:

- [ ] Does it follow parent-child semantics?
- [ ] Does it use existing patterns from `@repo/ui`?
- [ ] Is it composable with existing components?
- [ ] Does naming follow `[parent]-[child]` pattern?
- [ ] Is it documented with examples?

**Before Creating New Apps**:

- [ ] Is it a parent or child app?
- [ ] Does `.ideai.json` correctly define role?
- [ ] Does it follow parent-child app patterns?
- [ ] Can it be embedded if it's a child app?

**Before Creating New Scripts**:

- [ ] Does naming follow `ideai-[parent]-[child].mjs` pattern?
- [ ] Is it in the correct location?
- [ ] Does it follow existing script patterns?

## Development Workflow Standards

### Local Development Server Management

**CRITICAL**: Starting dev servers must follow a clear, predictable workflow to avoid confusion.

#### Primary Method: Turbo (All Apps)

**Command**: `pnpm dev`

**What it does**:

- Runs `turbo run dev --concurrency=20` from root
- Starts all 13 apps in parallel via Turbo
- Each app runs on its configured port (3000-3012)

**When to use**:

- ✅ Starting all apps at once

**If Turbo fails**:

- One app failure may stop Turbo or leave some apps not started
- Check which apps failed: Look for error messages in output
- Use fallback method (individual apps) to start remaining apps

#### Fallback Method: Individual Apps

**Command**: `pnpm --filter <app-name> dev`

**What it does**:

- Starts a single app in foreground
- Use `&` to run in background: `pnpm --filter web dev &`

**When to use**:

- ✅ Turbo failed and some apps didn't start
- ✅ Need to start specific apps only
- ✅ Debugging a specific app

**Example**:

```bash
# Start web app
pnpm --filter web dev &

# Start docs app
pnpm --filter docs dev &

# Start all apps individually (if turbo fails)
for app in web docs all nocss mvp tailwind allcss bootstrap unocss shadcn material chakra radix; do
  pnpm --filter $app dev &
done
```

#### Checking Server Status

**Method 1: Port Check** (Recommended)

```bash
# Check all ports
for port in 3000 3001 3002 3003 3004 3005 3006 3007 3008 3009 3010 3011 3012; do
  if lsof -ti:$port >/dev/null 2>&1; then
    echo "✅ Port $port: Running"
  else
    echo "❌ Port $port: Not running"
  fi
done
```

**Method 2: Process Check**

```bash
# Check for running Next.js processes
ps aux | grep -E "next dev|turbo.*dev" | grep -v grep
```

**Method 3: HTTP Check**

```bash
# Test if app responds
curl -s http://localhost:3000 >/dev/null && echo "✅ Web app responding" || echo "❌ Web app not responding"
```

#### Stopping Dev Servers

**Graceful Shutdown** (Recommended):

```bash
pnpm dev:stop
# Uses scripts/ideai-develop-graceful-shutdown.mjs
```

**Force Kill** (If graceful fails):

```bash
pnpm dev:stop:force
# Immediately kills all processes
```

**Manual Kill**:

```bash
# Kill all processes on dev ports
lsof -ti:3000,3001,3002,3003,3004,3005,3006,3007,3008,3009,3010,3011,3012 | xargs kill -9 2>/dev/null
```

#### Important Notes

1. **`dev-manager.mjs` doesn't exist**: Documentation may reference `scripts/dev-manager.mjs`, but this script does not exist. Use `pnpm dev` (Turbo) or individual `pnpm --filter` commands instead.

2. **Turbo concurrency**: The `dev` script uses `--concurrency=20` to handle all 13 apps. This is required because Turbo's default is 10, which is insufficient.

3. **App ports**: Each app has a fixed port defined in its `package.json` dev script:
   - web: 3000
   - docs: 3001
   - all: 3002
   - nocss: 3003
   - mvp: 3004
   - tailwind: 3005
   - allcss: 3006
   - bootstrap: 3007
   - unocss: 3008
   - shadcn: 3009
   - material: 3010
   - chakra: 3011
   - radix: 3012

4. **Submodules**: `apps/ideai-designer` is a submodule and is excluded from `pnpm dev`. Start it separately if needed: `cd apps/ideai-designer && pnpm dev` (runs on port 3013).

5. **Background processes**: When starting apps individually, always use `&` to run in background, or they will block the terminal.

#### Troubleshooting

**Problem**: Turbo fails with "command exited (1)"

- **Solution**: Check which app failed, fix the error, then start remaining apps individually

**Problem**: Some apps not starting

- **Solution**: Use port check to identify missing apps, then start them individually

**Problem**: Port already in use

- **Solution**: Use `pnpm dev:stop` to gracefully stop all servers, or manually kill processes on that port

**Problem**: Apps start but don't respond

- **Solution**: Wait 10-15 seconds for Next.js to compile, then check again. Check logs for compilation errors.

#### Workflow Checklist

**Before starting dev servers**:

- [ ] All dependencies installed (`pnpm install`)
- [ ] No processes on ports 3000-3012 (or stop existing ones)
- [ ] Submodules synced (if using ideai-designer)

**Starting dev servers**:

- [ ] Try `pnpm dev` first (Turbo method)
- [ ] Wait 15-20 seconds for all apps to start
- [ ] Check port status to verify all apps running
- [ ] If some apps failed, start them individually

**After starting**:

- [ ] Verify all 13 apps running (ports 3000-3012)
- [ ] Test at least web (3000) and docs (3001) in browser
- [ ] Check for compilation errors in terminal
